# Output Templates

Two artifacts. The primary is small and agent-facing; the secondary is detailed and human-facing.

## Primary artifact: `CLAUDE.md`

Hard cap: ~3–5k tokens. If you're over, cut detail, not structure.

```markdown
# Project Conventions

[1–2 sentence project description: what it is, primary languages, top-level architecture in one phrase. e.g., "Flutter mobile + web app with a Riverpod state layer and a thin REST client over a Dart-server backend."]

## Canonical conventions

These are the rules new code follows. Existing code generally matches these.

### Naming
- Files: [pattern] (e.g., `service_user.dart`, `widget_login.dart`)
- Types: [pattern]
- Functions: [pattern + verb conventions]
- Tests: [pattern]

### File organization
- [Where things live, concretely]
- Tests: [convention]
- Public API: [where exposed, how]

### Error handling
- [Pattern, with one exemplar reference]

### State management
- [Library + pattern]
- [Where state lives]

### Async
- [Convention]

### Testing
- [Framework, structure, mocking approach]

[Add other sections as needed from the checklist. Skip sections where the codebase has no convention — say so explicitly in the gaps section if relevant.]

## Aspirational conventions

These are the direction we're moving. New code should follow these. Existing code may not match yet.

- [Aspirational rule 1, with reason or migration target]
- [Aspirational rule 2]

## Legacy patterns — recognize, do not extend

You will encounter these in the codebase. Do not produce new code in these patterns. If you are modifying a file that uses a legacy pattern, prefer migrating it to the canonical equivalent only if the change is small and in scope.

- **[Legacy pattern 1]** — found in [where]. Migrate to [canonical pattern].
- **[Legacy pattern 2]** — found in [where]. Migrate to [canonical pattern].

## Exemplar files

When in doubt, read these as canonical references:

- [Layer / concern]: `path/to/exemplar.ext`
- [Layer / concern]: `path/to/exemplar.ext`

## Gaps

Conventions the codebase has no clear opinion on. The agent should ask before establishing one:

- [Concern with no current convention]
- [Concern with no current convention]

_Generated by codebase-conventions-distiller on [date]. Re-run the skill to refresh after significant changes or migrations._
```

## Secondary artifact: `CONVENTIONS_ANALYSIS.md`

No hard size cap, but stay disciplined. This is for human reference and for diffing on future runs.

## Notes on producing the primary artifact

- Be ruthless about cutting. If a section has only one bullet, consider whether that bullet belongs in another section.
- Prefer concrete to abstract. "Functions are named for what they do" is useless. "Async network functions are named `fetchX`; sync local accessors are named `getX`; cache-or-network operations are named `loadX`" is useful.
- One exemplar per layer is enough. The agent will read every cited file when it's relevant; citing five examples means five files of attention cost.
- If the codebase has fewer than three real conventions in a section, drop the section rather than padding.
- Mark aspirational items clearly. Mixing them in with canonical defeats the purpose.
